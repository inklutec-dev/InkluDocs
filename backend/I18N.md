# InkluDocs UI-Internationalisierung (i18n)

Stand: 02.07.2026 (Phase C). Sprachen: Deutsch (Quelle), Englisch, Französisch, Spanisch.

## Architektur in einem Absatz

Die UI-Sprache wird pro Request serverseitig aufgelöst und auf zwei Wegen
ausgespielt: Template-Texte über Jinja2 + Babel/gettext (`{{ _('...') }}`),
JavaScript-Texte über eine vom Server mitgelieferte Übersetzungstabelle
`window.I18N` und den Helfer `t('...')` in `frontend/static/dashboard.js`.
Beide Wege speisen sich aus denselben `.po`-Dateien — eine Quelle für alles.

## Sprach-Auflösung (4 Stufen, erste Treffer gewinnt)

1. Eingeloggter Nutzer: `users.language` aus der DB (gesetzt über die
   Einstellungen-Seite, Endpoint `GET /set-language/{lang}`)
2. Session-Cookie `lang` (Gäste nach manueller Wahl)
3. HTTP-Header `Accept-Language` (Browser-Erkennung)
4. Fallback: Deutsch

Code: `backend/i18n.py` (`detect_language`), `backend/main.py`
(`resolve_ui_language`, `_render_protected_template`).

## Dateien

- `backend/i18n.py` — Sprach-Erkennung, gettext, `template_context()`,
  `_catalog_json()` (baut `window.I18N`)
- `backend/templates/base.html` — Grundgerüst öffentliche Seiten (Login)
- `backend/templates/base_app.html` — Grundgerüst eingeloggter Seiten
  (App-Shell, Skip-Link, `window.LANG`/`window.I18N`, lädt dashboard.js).
  Blöcke: `title`, `head_extra`, `main`, `dialogs`, `page_script`
- `backend/locales/{de,en,fr,es}/LC_MESSAGES/messages.po` — Übersetzungen;
  `.mo`-Dateien werden beim Docker-Build kompiliert (`pybabel compile`),
  liegen nicht in Git
- `backend/babel.cfg` — Extractor-Konfiguration (aktuell werden neue
  Strings von Hand in die `.po`-Dateien eingetragen)

## Migrierte Seiten (Jinja2, viersprachig)

- `/` Login (`templates/index.html`, Phase POC 04/2026)
- `/einstellungen` (Phase A, 01.07.2026) — enthält das Sprach-Menü
- `/dashboard`, `/projekte`, `/projekt-neu` (Phase C, 02.07.2026)

Noch statisch (FileResponse aus `frontend/`, erscheinen deutsch):
`app.html` (größter Brocken), `benutzer.html`, register/forgot/reset,
Rechtsseiten, Demo-Seiten. Das Seiten-JS von `einstellungen.html` ist noch
nicht auf `t()` umgestellt (Meldungen dort kommen deutsch).

## Kochrezept: eine Seite migrieren

1. `frontend/<seite>.html` nach `backend/templates/<seite>.html` kopieren
   und auf `{% extends "base_app.html" %}` umbauen: nur noch die Blöcke
   `title`, `main`, ggf. `dialogs` (Overlays außerhalb von `<main>`) und
   `page_script` füllen. Kopf/Fuß/Sidebar liefert das Base-Template.
2. Sichtbare Template-Texte durch `{{ _('Deutscher Text') }}` ersetzen.
   Eindeutigen Seitentitel vergeben (`{{ _('Seitenname') }} · InkluDocs`) —
   wichtig für Screenreader-Orientierung (WCAG 2.4.2).
3. Seiten-JS in den `page_script`-Block, wörtlich in `{% raw %} ... {% endraw %}`
   (sonst frisst Jinja die `{...}`-Literale). Sichtbare JS-Strings durch
   `t('Deutscher Text')` ersetzen; Platzhalter im Muster
   `t('Hallo {name}', { name: x })`.
   ACHTUNG: Callback-Parameter nicht `t` nennen (verschattet den Helfer).
4. Alle neuen deutschen Strings in ALLE VIER `.po`-Dateien eintragen
   (msgid = deutscher Originaltext, auch für de — dort msgstr = msgid).
   Vorher auf Duplikate prüfen: doppelte msgids brechen `pybabel compile`
   und damit den Docker-Build.
5. Route in `main.py` von `_serve_protected_page` auf
   `_render_protected_template` umstellen.
6. Die alte Datei in `frontend/` bleibt vorerst liegen (Aufräumen erst,
   wenn alle Seiten migriert sind).
7. Staging bauen und in allen vier Sprachen testen (Titel, `<html lang>`,
   Inhalt, Sprachwechsel über /einstellungen).

## Barrierefreiheits-Pflichtpunkte

- `<html lang>` wird dynamisch gesetzt (macht base_app.html) — sonst liest
  der Screenreader englischen Text mit deutscher Stimme.
- Sprachwechsel lädt die Seite neu (Link-Navigation, kein Client-Swap) —
  Screenreader erkennen `lang`-Änderungen sonst nicht zuverlässig.
- Jede Seite braucht einen eindeutigen, übersetzten `<title>`.
- Sprachnamen im Menü stehen in der jeweiligen Landessprache
  ("English", nicht "Englisch").

## Bekannte Grenzen / offene Punkte

- `window.I18N` liefern nur base_app-Seiten. Auf noch statischen Seiten
  fällt `t()` auf den deutschen Ausgangstext zurück (die Sidebar bleibt
  dort deutsch, das ist der eingebaute Fallback, kein Fehler).
- Server-Daten bleiben deutsch: Werkzeugnamen/Status aus `/api/tools`,
  Neuigkeiten aus `/api/news`, API-Fehlertexte (`detail`).
- FR/ES sind Claude-Erstübersetzungen — Muttersprachler-QA vor Prod.
- VOR Prod-Rollout: Cache-Busting für statische JS/CSS einbauen, sonst
  laden Bestandsnutzer die alte dashboard.js aus dem Browser-Cache und
  sehen gemischte Sprache.
- Die Sprache der GENERIERTEN ALT-TEXTE ist bewusst getrennt von der
  UI-Sprache (eigenes Feature, pro Projekt/Bild).
